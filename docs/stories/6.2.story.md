# Story 6.2: Declarar dependências e garantir instalação limpa reproduzível

## Status

Ready

## Story

**As a** consultor/desenvolvedor configurando o ambiente do Data Catalog & Profiler em uma máquina nova (clone limpo do repositório),
**I want** que o manifesto de dependências declare todos os pacotes efetivamente importados pelo código e que a relação entre os dois manifestos existentes seja resolvida sem ambiguidade,
**so that** `pip install -r <manifesto>` seguido de `streamlit run` funcione sem nenhum `ImportError`, desbloqueando o restante do roadmap (Epic 1 e a baseline de testes da Story 6.3).

## Dependencies

- **Depende de:** nenhuma story (primeira da sequência recomendada pelo @pm).
- **Bloqueia:** Story 6.3 — o smoke test de import de todos os módulos de `src/` (6.3 AC4) importa `src/core/deduplicator.py`, que hoje importa `numpy`, `sklearn` e `rapidfuzz` sem que nenhum dos três esteja declarado em `requirements_catalog.txt`; sem esta story, o smoke test falha por ambiente, não por bug.
- **Ordem de execução recomendada pelo @pm** (`docs/prd/README.md` §3): 6.2 → 6.3 → 1.1 → 1.2 → 1.3. Esta é a story 1 de 5 dessa sequência.

## Acceptance Criteria

Copiado literalmente de `docs/prd/epic-6-debito-tecnico-plataforma.md` (Story 6.2):

1. `requirements_catalog.txt` passa a declarar **todas** as dependências efetivamente importadas pelo código, incluindo `numpy`, `scikit-learn` e `rapidfuzz` (`deduplicator.py:1-5`), com versões mínimas.
2. Auditoria completa: todo import de terceiros em `src/` é cruzado com o manifesto; a lista de discrepâncias é reportada e zerada.
3. A relação entre `requirements.txt` e `requirements_catalog.txt` é resolvida — consolidação em um único manifesto ou documentação explícita de qual serve a quê. Ambiguidade de manifesto não permanece.
4. **Teste de instalação limpa:** em virtualenv novo, `pip install -r <manifesto>` seguido de `streamlit run` permite navegar nas duas telas (Profiling e Duplicidades) sem nenhum `ImportError`. O procedimento é documentado e reproduzido por outra pessoa que não a autora.
5. Instruções de setup do ambiente documentadas (versão de Python suportada, criação de venv, execução).
6. Nenhuma dependência é adicionada sem uso real no código (o inverso do débito atual).

### RESOLVIDO — AC1 × AC6 sobre `rapidfuzz`: declarar normalmente (decisão do @po, 2026-09-09)

**Não há conflito entre a AC1 e a AC6. `rapidfuzz` DEVE ser declarado nesta story. Isto não é uma questão em aberto para o executor decidir.**

Achado verificado (re-confirmado em 2026-09-09, leitura integral de `src/core/deduplicator.py`): a linha 5 executa `from rapidfuzz import fuzz`, mas o símbolo `fuzz` **nunca é chamado** em nenhum ponto do arquivo — a lógica de similaridade de `find_duplicates` usa `TfidfVectorizer` + `cosine_similarity` (linhas 31-35) e `np.where` (linhas 49, 76). `rapidfuzz` é, portanto, um **import morto**. [Source: src/core/deduplicator.py — lido integralmente, 2026-09-09]

Resolução, com o critério explicitado para não deixar margem de interpretação:

- **A AC1 governa esta story.** Ela pede declarar o que está **efetivamente importado pelo código hoje**. Um import morto ainda é executado no carregamento do módulo: sem `rapidfuzz` instalado, `import src.core.deduplicator` levanta `ImportError` e a tela de Duplicidades não abre. Omitir o pacote quebraria a instalação limpa exigida pela AC4 e o smoke test da Story 6.3 (AC4 de lá).
- **"Uso real" na AC6 significa "é importado e necessário para o módulo carregar sem `ImportError`"** — não "toda função importada é de fato chamada downstream". A AC6 existe para impedir o inverso do débito atual (declarar pacote que o código nem importa, como `anthropic`/`mcp` em `requirements.txt`), não para transformar esta story em uma caçada a código morto.
- **Remover o import morto é escopo da Story 6.1** (débito de escalabilidade/qualidade do `deduplicator.py`), **não desta story.** Se e quando a 6.1 remover a linha 5, `rapidfuzz` poderá sair do manifesto — nesse momento, e não antes. Registrar essa dependência de escopo no Dev Agent Record para que o quality gate da 6.1 encontre o contexto.
- **Ação concreta para o executor:** declarar `rapidfuzz` na Task 2 junto com `numpy` e `scikit-learn`, e adicionar comentário no manifesto marcando-o como import de `deduplicator.py` pendente de revisão na Story 6.1. Nenhum AC precisa ser alterado; nenhuma decisão adicional é necessária.

### Risco de instalação: wheels binárias de `numpy`/`scikit-learn` em Windows

O ambiente-alvo deste projeto é **Windows** (Windows 11 Pro, ambiente do usuário — o mesmo onde o teste de instalação limpa da AC4 será executado). `numpy` e `scikit-learn` são pacotes com extensões compiladas em C/C++/Fortran e dependem de **wheel binária pré-compilada** para a combinação exata de versão de Python + plataforma. Implicações práticas para a Task 2 e a Task 4:

- Se a versão mínima escolhida não tiver wheel `win_amd64` para a versão de Python usada, o `pip` tentará compilar a partir do source e falhará (exige MSVC Build Tools / toolchain Fortran) — o sintoma aparecerá como falha de build, não como `ImportError`, e pode ser confundido com erro de manifesto.
- Ancorar a versão mínima do Python (AC5) **antes** de fixar os pisos de versão de `numpy`/`scikit-learn`, e escolher pisos que comprovadamente tenham wheel para essa combinação. `scikit-learn` puxa `numpy` e `scipy` transitivamente — deixar o resolver do pip harmonizar as versões em vez de fixar pisos agressivos demais.
- A Task 4 (instalação limpa em venv novo) é o ponto onde esse risco se materializa ou se descarta. Se o `pip install` falhar por build de wheel, isso é achado da AC4 e deve ser documentado no Dev Agent Record com a mensagem de erro completa — não contornado com instalação manual fora do manifesto, o que invalidaria a reprodutibilidade exigida pela AC4.
