# Story 1.2: Migração idempotente de schema no metadata store

## Status

Ready

## Story

**As a** desenvolvedor que vai adicionar colunas/tabelas ao metadata store em stories futuras (Epics 2 a 5),
**I want** uma função de migração idempotente e versionada, aplicada na abertura de cada workspace, que evolua bases `metadata.db` existentes sem perda de dados e sem `DROP TABLE`,
**so that** qualquer story futura possa adicionar campos ao glossário sem quebrar bases já em uso pelos consultores, e sem risco de estado parcialmente migrado em caso de falha.

## Dependencies

- **Depende de (técnico, hard):** Story 1.1 — a AC1 desta story define a migração como executada "na abertura de todo workspace"; o conceito e a resolução de workspace só existem após a Story 1.1 estar implementada.
- **Depende de (recomendado pelo @pm):** Story 6.3 — rede de segurança de testes antes de introduzir uma camada de versionamento de schema que toca em todas as bases existentes.
- **Bloqueia:** Story 1.3 (apenas por ordem de sequência recomendada — não há dependência técnica direta documentada entre 1.2 e 1.3 no epic). Bloqueia também as Stories 2.2, 3.2, 3.3, 4.2 e 5.1, que dependem da documentação de "como adicionar uma nova migration" (AC8 desta story), conforme listado explicitamente no epic.
- **Ordem de execução recomendada pelo @pm** (`docs/prd/README.md` §3): 6.2 → 6.3 → 1.1 → 1.2 → 1.3. Esta é a story 4 de 5 dessa sequência.

## Acceptance Criteria

Copiado de `docs/prd/epic-1-fundacao-tecnica.md` (Story 1.2). **Exceção:** a AC3 foi ajustada pelo @po para refletir o caminho pós-Story 1.1 — ver nota de reconciliação logo abaixo da lista.

1. Existe uma função de migração (ex.: `migrate_db(conn)`) executada na abertura de todo workspace, com versão persistida via `PRAGMA user_version` ou tabela `schema_version` dedicada.
2. A migração é **idempotente**: executá-la N vezes consecutivas produz exatamente o mesmo schema, sem erro e sem efeito colateral.
3. A migração se aplica a bases legadas criadas pelo `init_db()` atual (`glossary.py:6-24`, schema sem versionamento) sem perda de dados — incluindo a base originada do `metadata.db` legado, que na ordem de execução recomendada (6.2 → 6.3 → 1.1 → 1.2 → 1.3) **já terá sido migrada pela Story 1.1 (AC7) para `data/workspaces/{workspace_slug}/metadata.db`** (raiz configurável por `CATALOG_DATA_DIR`, Story 1.1 AC3). O alvo de validação desta AC é, portanto, o arquivo do workspace resultante da 1.1 — que continua em schema v0, pois a 1.1 apenas o realoca, sem alterar seu schema. Se, por qualquer razão, o `metadata.db` legado ainda existir na raiz do projeto no momento da execução desta story, isso indica que a Story 1.1 AC7 não foi concluída — situação a ser tratada como bloqueio, não contornada migrando o arquivo da raiz diretamente.
4. Adição de coluna usa `ALTER TABLE ... ADD COLUMN` com verificação prévia via `PRAGMA table_info`. É **proibido** `DROP TABLE` ou recriação de `glossary` como estratégia de evolução.
5. Cada execução registra em log a versão de origem, a versão de destino e as migrations aplicadas.
6. Falha de migração aborta a abertura do workspace com mensagem acionável e **não deixa a base em estado parcialmente migrado** (migração dentro de transação, com rollback em erro).
7. Testes automatizados cobrem no mínimo: (a) base nova criada do zero, (b) base legada em schema v0 sem versionamento, (c) reexecução sobre base já migrada (idempotência), (d) falha simulada com verificação de rollback.
8. Existe documentação curta de "como adicionar uma nova migration", referenciada pelas stories dependentes (2.2, 3.2, 3.3, 4.2, 5.1).
9. **Regressão:** `save_metadata`, `get_metadata` e `get_all_metadata` continuam com o mesmo contrato e comportamento após a migração.

### Nota de reconciliação da AC3 (@po, 2026-09-09)

O texto original da AC3 no epic termina com "— incluindo o `metadata.db` hoje presente na raiz do projeto". Esse texto foi escrito na perspectiva do estado atual do repositório, **antes** da Story 1.1 existir. Como a 1.1 é dependência hard desta story e sua AC7 exige justamente migrar o `metadata.db` legado da raiz para um workspace nomeado, o caminho citado no epic já não existirá quando esta story for executada. Manter a redação literal levaria o executor a procurar (ou pior, a escrever em) um arquivo na raiz que a 1.1 deve ter esvaziado.

- **Intenção preservada:** a AC continua exigindo que a migração funcione sobre a base legada real em schema v0, sem perda de dados. Nada foi afrouxado.
- **O que mudou:** apenas a referência de caminho, de `metadata.db` na raiz para `data/workspaces/{workspace_slug}/metadata.db` (o destino definido pela Story 1.1 AC3/AC7).
- **Texto do epic:** não alterado. A divergência está registrada aqui e no Change Log; se o epic for regenerado, esta reconciliação deve ser reaplicada.

### Previous Story Insights

Esta story depende diretamente da Story 1.1 (resolução de workspace) — revisar o Dev Agent Record da 1.1 antes de iniciar, em particular: (a) onde exatamente ficou o ponto de "abertura de workspace" ao qual `migrate_db(conn)` deve se acoplar, e (b) qual biblioteca/abordagem de conexão SQLite a 1.1 usou (`sqlite3` puro, como hoje, ou alguma camada adicional), para manter consistência.

### Contexto e achados verificados no código (2026-09-09)

- `src/models/glossary.py:6-24` — `init_db()` atual executa apenas:
  ```sql
  CREATE TABLE IF NOT EXISTS glossary (
      schema_name TEXT,
      table_name TEXT,
      column_name TEXT,
      business_name TEXT,
      description TEXT,
      domain_values TEXT,
      classification TEXT,
      is_mandatory BOOLEAN,
      is_unique BOOLEAN,
      PRIMARY KEY (schema_name, table_name, column_name)
  )
  ```
  Este é exatamente o "schema v0 sem versionamento" que a AC3 exige suportar. [Source: src/models/glossary.py]
- `src/models/glossary.py:26-50` (`save_metadata`), `52-72` (`get_metadata`), `74-95` (`get_all_metadata`) — cada função abre e fecha sua própria conexão SQLite (`sqlite3.connect(DB_FILE)` / `conn.close()`), sem transação explícita de longa duração. A função de migração precisa se acoplar ao ponto de abertura de conexão por workspace (definido na Story 1.1), não a cada chamada individual dessas três funções. [Source: src/models/glossary.py]
- Não existe hoje nenhuma tabela `schema_version` nem uso de `PRAGMA user_version` no código — a decisão entre as duas abordagens (AC1) é do executor; ambas são válidas para SQLite.
- O epic é explícito e a AC4 é bloqueante: `DROP TABLE` ou recriação de `glossary` **não** é uma estratégia aceitável, mesmo que mais simples de implementar.

### Arquitetura / Padrões do Projeto

Não há `docs/architecture/` sharded neste projeto. Este é o primeiro documento formal de estratégia de migração do projeto — a documentação produzida na Task 8 (AC8) torna-se a referência oficial para as stories dependentes (2.2, 3.2, 3.3, 4.2, 5.1); não existe convenção anterior a seguir.

- O caso (d) da AC7 (falha simulada com rollback) exige alguma forma de injeção de falha controlada (ex.: mock de uma etapa de migration para lançar exceção no meio de uma sequência multi-tabela) — documentar a técnica escolhida no Dev Agent Record.
